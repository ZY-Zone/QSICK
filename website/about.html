关于 QSICK

ZY-Zone · QSICK--QQ_NT-Bridge

QSICK 是一个基于原生注入的 QQNT API 导出工具：把 QQNT 的收发能力导出成 OneBot v11 与 Milky， 让 QQ 重新成为可编程的基础设施。项目由 ZY-Zone 维护，源码与文档都公开在 GitHub。

01项目

QSICK 要回答的是一个很具体的问题：QQNT 没有开放的机器人接口。 常见做法无非三种——模拟点击与截图识别，脆弱且只能覆盖眼睛看得见的功能；Electron 套壳， 把整个客户端再包一层；或者解析网络流量，被加密和版本更新反复挡住。 QSICK 选择第四条路：原生注入。

内核通过注入器把 C++ payload 注入 QQ.exe，payload 在 QQ 的收发路径上挂接钩子， 通过命名管道把事件与动作送进内核；内核再按每条连接自己的协议，把它们编码成 OneBot v11 或 Milky。 你拿到的不是屏幕里能点到的东西，而是客户端真正能做的事。

主要能力

  • 原生 payload 注入：C++ DLL 负责命名管道、钩子引擎与跳板，32 字节帧头 + JSON 体；偏移表驱动，可逐版本替换。
  • OneBot v11 / Milky 双协议：同一实例可以同时挂两种协议，事件与动作按连接各自编解码，互不串味。
  • 插件系统：清单 + 权限 + 生命周期钩子，支持热重载、配置界面扩展与远程插件市场；故障隔离到单个插件。
  • 多实例：headless 与 pipe 两类实例，模板硬链接、数据目录重定向，每个实例有自己的消息库与网络配置。
  • WebUI：FastAPI + Jinja2 面板，仪表盘、SSE 实时日志、动作测试器与消息库，都在 127.0.0.1:5754。
  • maxStore 证据库：收到的原始 payload 先完整落库，再分发给协议连接；历史数据不会只剩当时那个协议要的字段。

技术栈

  • 原生侧：C++ DLL payload（MSVC，/MT 静态链接，只依赖 KERNEL32 与 ADVAPI32，不需要 VC++ 运行时）。
  • 内核：Python——实例中心、协议适配、动作注册表、插件宿主与 maxStore 都在这里。
  • 前端：FastAPI + Jinja2 提供 HTTP / WebSocket / SSE；图表是手写 SVG，没有前端框架，也没有 Electron。

边界

  • 不在 QQ 内执行 JavaScript。QSICK 不是 JS 运行时，插件与协议适配都在内核里。
  • 登录与包签名尚未实现。加密属于 payload 的职责，目前仍是路线图上的阻塞点；QSICK 依赖真实的 QQNT 客户端运行时，而不是自己复刻一套协议栈。

更完整的实现细节与路线图在 架构文档。

02设计取舍

QSICK 的很多决定，来自不愿意把问题藏起来。下面几条写在仓库文档里， 也决定了这个页面必须存在。

为什么这样切

必须跑在 QQ.exe 里的代码是原生实现，其余全部是 Python。 docs/architecture.md · 为什么这样切

这是一条不可移动的分界线。内联钩子、跳板与调用约定需要原始内存访问和逐版本偏移， 只能留在 C++ payload；消息语义、OneBot 映射、插件与 WebUI 放进 Python 内核， 可以热重载，可以对着 MockTransport 测试，改字段不需要重新编译。

动作这一层还有一道约束：处理器从不直接接触管道或 payload。 能力统一通过 ActionContext 暴露，注册表在入口做校验与分发—— 这既是可测试性的来源，也是插件权限能真正生效的前提。

代价必须写在明处

注入类工具会让登录态暴露在额外的攻击面上。不要在主力账号上使用，更不要在公用或来路不明的机器上运行。 README · 免责声明

攻击面没法靠一句「注意安全」消除，能做的只有把它限制在明处： 命名管道使用 owner / SYSTEM / Administrators 的 DACL，每次会话带 128 位令牌， 随机模式下令牌同时出现在管道名与 HELLO 帧里，对不上就拒绝。 除此之外，请使用一次性账号。

一条不能让步的约束

动作必须经过 runtime.invoke。绕开它直接把调用转给宿主，core 插件的封禁就形同虚设——而那从外面完全看不出来。 docs/PROTOCOLS.md · 一条不能让步的约束

插件过滤、账号级出入限制、只读缓存、发送串行化全在这一个入口上。 协议适配层只负责把请求翻译成内部名字，不做决定；少一次「聪明」的绕过， 就少一类从外面看不见的漏洞。

四条小原则

真实性 maxStore 先把原始 payload 完整落库再分发：整包 JSON 与摊平字段各留一份。冗余是刻意的——将来字段改名、嵌套加深，旧数据仍然取得到。
可观测性 仪表盘、SSE 实时日志与动作测试器在同一个面板里。「发生了什么」应该一眼能看到，而不是去翻进程内存。
失败可诊断 payload 中途死掉只推送 runtime.closed；单个插件抛异常只跳过该插件；解码失败向上抛，回一个明确的失败，而不是让客户端等到超时。
最小惊讶 看不懂的元素变成 unknown 段并保留原始载荷，解码器不会悄悄清空一条消息；计划中的动作返回明确的 retcode，而不是假装成功。
