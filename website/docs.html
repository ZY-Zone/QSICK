01快速开始

QSICK 在 Windows 上只有一个入口：仓库根目录的 start.bat。首次运行会依次完成三件事：用 uv 安装 Python 依赖、从联网服务器获取 QQNT-9.9.33-52230 运行时、启动 WebUI 并在几秒后自动打开 http://127.0.0.1:5754/。

Windows：双击 start.bat

把仓库完整克隆到本地（运行时与实例目录不入库，必须由脚本自行准备），双击 start.bat。依赖安装与运行时下载都会花一些时间；下载完成后 runtime\ 会保留，后续启动直接复用。

如果网络条件允许，也可以先双击 获取QQnt.bat 预下载官方安装包并解包到 runtime\，这样首次启动不必再等待。该脚本额外支持 --force（重新下载）、--clean（清空 runtime\ 后解包）与 --source X.exe（使用本地安装包，完全不联网）。

bat
start.bat            :: 首次初始化 + mock 传输 + WebUI（安全的默认值）
start.bat --check    :: 只检查 uv / node / Python 依赖，然后退出
start.bat real       :: 附着到已运行的 QQ.exe，走原生 payload

--check 会打印 uv 版本、检查 node（headless 宿主需要 Node.js 18+），并确认 fastapi、uvicorn、jinja2 可以导入；依赖缺失时它会顺手执行一次 uv sync，但不会启动内核。启动前脚本还会预检 5754 端口：若已被其他程序占用（例如 SnowLuma），会提示用 set QSICK_WEBUI_PORT=5098 与 set QSICK_ONEBOT_PORT=3001 改端口重试。

源码运行

需要 Python 3.12+ 与 uv。三条命令依次完成：安装含测试依赖的开发环境、以可编辑模式安装项目、用 mock 传输启动内核。

bash
uv sync --extra dev
uv pip install -e . --no-deps
uv run qsick --mock

mock 模式

--mock 使用 MockTransport：事件与动作都在进程内合成，不启动 QQ、不登录账号、也不会连接 QQ 服务器。WebUI、动作注册表、插件与存储仍然是真实代码，所以可以先把整条链路跑通，再切换到真实实例。这也是 start.bat 默认选择 mock 的原因——默认值不应该要求一个已登录的账号。

设置密码与 token

WebUI 默认监听回环地址，但不会替你设置密码。首次访问时页面底部会出现一条引导横幅，可在设置 → 安全与隐私设置密码；密码只保存 scrypt 摘要，明文不落盘，会话 30 分钟、有操作即续期。给脚本或客户端用的共享密钥是 webui.access_token，与密码并存，任一通过即可访问。

OneBot 侧的 onebot.access_token 在网络页按每条配置设置；HTTP / WS / SSE 都用 secrets.compare_digest 比对，反向 WebSocket 则把同一令牌放在 Authorization: Bearer 头里。没有 token 时不要监听公网地址。

先读免责声明。QSICK 会向 QQ.exe 注入代码并接管其收发路径，这可能违反腾讯用户协议，并导致账号被限制、封禁或永久终止。仅限学习与研究，请使用一次性账号，不要在主力账号或公用机器上运行。

02架构

QSICK 沿一条不可移动的分界线切开：必须跑在 QQ.exe 里的代码是原生实现（C++ DLL），其余全部是 Python。内联钩子、跳板与逐版本偏移留在 payload；消息语义、动作映射、插件与 WebUI 用可热重载的 Python——改字段不需要重新编译 DLL。

flow
QQ.exe（QSICK payload · C++）
  │  命名管道  \\.\pipe\qsick.<pid>.ctl / .evt
  │  帧协议    32 字节头 + JSON 体
  ▼
qsick 内核（Python · FastAPI）
  ├─ 实例中心     每实例自己的消息库、处理器与网络配置
  ├─ 事件流水线   解码 → 插件钩子 → OneBot 事件 → WebSocket / SSE
  └─ 动作流水线   注册表 → ActionContext → transport.send(op, params) → payload

多实例：一条消息的归属

消息处理已经从"一个全局运行时"下放到每个实例。一个实例（C0、C1 …）在 QQ 侧就是一个登录的号，拥有自己的消息数据库、消息处理器与一组网络配置。

  • QQ 宿主的事件先进入该实例的消息处理器，而不是某个全局单例。
  • 先由 maxStore 把原始 payload 完整落盘，再按该实例每条网络配置的协议编码分发；顺序不能反——先裁剪再存，历史数据就只剩当时那个协议要的字段。
  • 动作从哪条连接来，就属于哪个实例，归属写在配置上，因此动作不需要 account 字段。

消息流水线

pipeline
宿主机事件
  → HeadlessTransport.push（按实例归类，附带 instance / account）
  → Runtime._handle
      · login 事件        → 该实例的 LoginState
      · message.*         → Message.from_payload
          → PluginHost.dispatch_message（守卫可在此丢弃，最省的一步）
          → 实例库 put（maxStore：原始 payload + 解析后字段合并）
          → MediaResolver（rkey → URL）
          → EventMapper.message → OneBot 事件
      · notice / request / meta → EventMapper.map
      · noise.*            → 仅 TRACE 日志（默认永不外发）
  → PluginHost.dispatch_event（只读观察者）
  → EventHub.broadcast → WebSocket / SSE 客户端
  • 先丢弃，再干活。插件在 URL 解析之前就看到 Message，守卫不必为一张即将被丢弃的图片去取 rkey。
  • 看不懂的是数据，不是错误。未识别的元素变成 unknown 段，保留原始类型与载荷；解码器永远不会把一条消息悄悄清空。
  • 噪声只进 TRACE。输入状态/正在输入事件写入 Noise 日志器，级别 TRACE；配置里的 forward_noise 是唯一能把它们放出来的开关。

动作：一个动作一个模块

onebot/actions/actions.json 是注册表；每条记录指名 onebot/actions/<类别>/<名称>.py 下的模块与实现类。加载器只导入列出的模块，因此某个动作坏掉只是一个孤立的导入错误，而不是启动失败。加一个动作只碰两个文件；把 status 翻一下，就是"计划中的占位"与"可用处理器"的区别。

json
{
  "name": "send_group_msg",
  "module": "message/send_group_msg",
  "class": "SendGroupMsgAction",
  "category": "message",
  "status": "implemented",
  "params": [{"name": "group_id", "kind": "int", "required": true}]
}

当前 242 条目录项全部已是 implemented；QQ 能否真的执行由运行时判定（不支持的 op 回 1502）。测试用的 verify_catalog() 会检查每条 JSON 都有模块、有类，并且真的覆写了 run()。

动作分发与失败姿态

一次调用的路径是：OneBot 请求 → runtime.invoke → ActionRegistry.dispatch → ActionContext.call(op) → transport.send(op, params) → payload 在 QQ 侧执行 → JSON 结果。ActionContext 是处理器唯一能碰到的面：transport、config、store、rkey、媒体解析器与登录状态。处理器从不直接接触管道或 payload，因此可以对着 MockTransport 测试。

情况返回
动作名未知retcode 1404
计划中但尚未接线retcode 1405，附提示
参数非法retcode 1400
处理器抛异常retcode 1500，带堆栈记日志
payload 侧不支持该 opretcode 1502，由传输层上报

失败时的姿态：能局部失败的不要升级成全局失败，能明确报错的不要静默跳过。

失败行为
payload 缺失 / 管道不存在启动报错，附上期望路径与环境变量
payload 中途死掉transport 推送 runtime.closed，记日志并继续提供 WebUI
某个事件处理器抛异常记日志、跳过该事件、循环继续
某个插件抛异常记日志、该事件跳过该插件、其它插件照常
某个 WS 客户端很慢它的队列丢掉最旧帧；其它客户端不受影响
rkey 刷新失败回落到静态/env 值，再不行媒体 URL 留空（id 保留）

一条不能让步的约束

动作必须经过 runtime.invoke。插件过滤、账号级出入限制、只读缓存与发送串行化全在它的入口。绕开它直接把调用转给宿主，core 插件的封禁就形同虚设——而从外面完全看不出来。

反向 WebSocket、认证与持久化

  • 反向 WebSocket。onebot.reverse_ws_urls 让 QSICK 成为拨号方：发送 X-Self-ID、X-Client-Role: Universal，配置了令牌则再发 Authorization: Bearer <token>。连上之后的行为与入站 WS 一致——发生命周期事件、收动作、发事件；重连按 URL 各自退避，失败不会波及 HTTP/WS 监听器。
  • 认证。HTTP / WS / SSE 用 secrets.compare_digest 比对 onebot.access_token；反向 WS 在 Authorization 头里发送同一个令牌。管道认证另有三种模式（random / fixed / none），细节见 Payload ABI。
  • 持久化。每个实例一个库：data/instances/C1/messages.db，后端是 maxStore。每条 payload 落两个粒度——整包 JSON（raw_json）与按 JSON 指针摊平的字段表（raw_frames）。冗余是刻意的：整包保证能原样还回去，摊平表保证字段改名、嵌套加深之后旧数据仍能按路径取出来。

03协议层

QSICK 把「协议」从功能里拆出来，放在项目根的 protocols/ 下：每个目录就是一份实现，目录名即协议名。enabled_protocol.json 是网络配置协议下拉框的可选项清单；清单与磁盘不一致时明确报错，不静默跳过——少一个协议比多一个错更容易查。

目录角色说明
onebotv11/聊天OneBot v11。默认协议；事件本来就是 v11 形状，转换是恒等。
milky/聊天Milky（v1.3）。调用 POST /api/{api}、推送 GET /event，带 {status, retcode, message, data} 信封。
maxStore/存储不是聊天协议，不可被选作聊天协议。保留收到的全部原始信息，包括未知字段与未识别元素。

三条流水线

流水线事件推送动作执行说明
maxStore✅❌只写消息缓存。它是汇不是通道：没有连接、没有端口。
onebotv11✅✅默认协议，转换恒等。
milky✅✅事件与调用名都要翻译。
pipeline
进（事件推送）
QQ 宿主 → runtime._dispatch_event → runtime._publish
  ├─ ① maxStore：原始 payload 先落该实例的库（先于一切裁剪）
  └─ ② 按每条连接自己的协议编码后投递
       → HTTP / WS / SSE / 反向 WS

出（动作执行）
连接 → pipeline.decode_action（该连接的协议）→ runtime.invoke
  └─ 插件过滤、账号级出入限制、只读缓存、发送锁全在这里

为什么协议要跟着连接走

EventHub 与反向 WS 客户端各自登记一个 Connection：谁连上来的、用哪条配置、什么协议、哪个账号。分流点只读它，不认识任何具体协议。改动前这一切并不存在——protocol 字段存在配置里、显示在下拉框里，但一条消息进来后所有连接收到的 JSON 完全相同；同一实例下挂一条 onebotv11 和一条 milky，两条都收到 v11 形状。

失败怎么处理

两个方向相反，这是刻意的：

  • 事件编码失败：只跳过走那个协议的连接，其余照发。一条消息喂不了某个协议，不该让所有客户端都收不到；同一个错误只打一行 WARN，避免日志被刷满。
  • 动作解码失败：向上抛，调用方回一个明确的失败。静默跳过会让客户端一直等到超时，而它发出的调用其实早就被拒绝了。

Milky 端点与 65/65 覆盖

URL 里不带协议前缀。一条连接说什么协议，由它落在哪条网络配置上决定，而不是由路径猜。协议是网络配置的属性，路径是那张配置自己的字段。

OneBot v11Milky
调用POST {path}（动作名在 body 里）POST {path}/api/{api}（动作名在路径里）
调用体{action, params, echo}参数直接是 body，至少要 {}
应答{status, retcode, data, echo}{status, retcode, message, data}
推送GET {path}（SSE/WS）GET {path}/event（SSE/WS，SSE 帧为 event: milky_event）
健康检查GET /health—

配置里的路径对这条配置的所有传输生效：v11 的同一个 URL 上 POST 跑动作、GET 推事件、Upgrade 建 WebSocket；Milky 的路径是基路径，填 / 就是 /api/{api} 与 /event，填 /bot 就是 /bot/api/{api} 与 /bot/event。端口按地址分组监听：HTTP 与 WS 写同一 host:port 时共用一个监听器，写不同地址时各自起一个 server。旧前缀（/ONEBOTV11/、/MILKY/）已移除——多一个别名就多一条会被误用的路径。

类数量含义调用结果
SUPPORTED + DYNAMIC53已登记动作映射，不代表底层与返回字段全部可用按已有能力执行或明确失败
NEEDS_TRANSLATION8请求审批标识缺转换明确失败并说明差什么
NO_ACTION1转存永久文件尚无对应能力明确失败并说明
UNSUPPORTED_BY_DESIGN2会话置顶读写不实现明确失败并说明
LOCAL1get_impl_info，适配器自己回答本地返回；QQ 版本未知时为空

65 / 65 个 Milky API 全部归类，但"归类"不等于"完整合规"：消息段双向都借道 v11 编解码（内部动作层按 v11 段解析，新协议必须把自家段编成 v11 形状）；一条内部事件可以产出多条协议事件（好友私聊里的文件消息同时是 message_receive 与 friend_file_upload）；身份取请求里的 account，不取随时会变的全局主账号。群通知序号、请求审批、44 包操作人等仍有缺口，不能仅凭事件名已有转换器就宣称完整符合字段契约。

加一个新协议

  1. 在 protocols/ 下新建目录，导出 create()。
  2. 在 enabled_protocol.json 的 chat 数组里登记。
  3. 在网络配置里选中它，即可按连接生效。
方法必须作用
encode_message / decode_message✅消息段 ⇄ 内部部件
encode_action✅内部动作 → 本协议的请求体
capabilities✅能表达什么、要降级什么
encode_event有默认内部事件 → 本协议事件（默认恒等，即 v11）
encode_events可选内部事件 → 若干本协议事件；不实现时用 encode_event 的单个结果
decode_action有默认本协议调用名 → 内部动作名（默认恒等）
format_reply有默认内部结果 → 本协议应答信封（默认恒等）

后四个有默认实现，所以只做消息格式的适配器不用管它们。encode_events 不是为将来预留：返回 dict 还是 list 都会被接受，实现其中一个即可。protocols/onebotv11/ 是最小样板，protocols/milky/ 是完整例子。

已移除的协议

onebotv11-EXTemotions 已移除：它是纯 v11 的严格超集，两个协议的差别只在一个 WebUI 聊天栏的发送路径上，而聊天栏已经删除，没有任何消费方。带走的还有 EXTemotions 数据模型、CQ:ext_emotion 解析与表情素材导入工具。

04实例

QSICK 的每个账号是一个实例。实例放在 headlessClient/ 下，目录名是稳定的 C0、C1……，同时有一个可改的显示名——改名不会让配置或数据库失联。

headless（默认）pipe
怎么跑裸 Node 直接 require runtime/wrapper.node启动原版 QQ.exe，再注入 payload DLL
谁提供 Electron没有（自造 QQNT.dll 垫片补符号）QQ 自己的 Electron 主进程
界面无（扫码在 WebUI）原版入口会建窗口，注入后隐藏
磁盘几乎不占，全实例共用一份 runtime/每实例一份完整客户端（约 1.1 GB 表面体积）
native 能力只有 wrapper.node 暴露的那些完整，原生环境就是原版那份
适合批量挂号、只要协议收发需要完整原生环境

创建

WebUI 的账户管理 → 新建实例会打开一个对话框：实例名称必填且不可重复（大小写不敏感，客服A 与 客户a 视为相同，最长 32 个字符）；实例类型选 headless 或 pipe，选中后在下方显示该类型的代价与收益。对应接口：

http
POST /api/accounts
Content-Type: application/json

{"name": "客服A", "kind": "pipe"}

两个字段都可省略：不带 body 时按"下一个 C<n> + headless"创建，保持与旧脚本兼容。名称冲突或类型非法返回 400，模板/磁盘问题返回 500。

模板：硬链接，不是复制

pipe 实例不能靠"写几个 json"建出来——它要能立刻启动，就得有 QQ.exe、versions/<版本>/resources/app/wrapper.node 与全部依赖 DLL。所以先从一份官方客户端生成模板（instanceTemplates/pipe-9.9.33-52230/），之后每次建实例把它铺过去。

一份客户端约 1868 个文件、1.1 GB；真复制 5 个实例就是 5.5 GB，而其中 99% 是一模一样的只读 DLL 与资源。铺实例时文件全部用 os.link 建硬链接——模板的 inode 等于实例的 inode，磁盘上只存一份数据。实测生成模板 0.4 秒（linked=1868 copied=0），建一个实例 0.5 秒 / 1871 个文件，磁盘几乎不增。跨卷或不支持硬链接时自动退回复制：宁可占空间，也不能建不出来。

模板生成与实例铺设时会顺手做三件事，否则"复制过去"并不等于"能用"：

  1. 对齐版本。把 resources/app/package.json 的 version 改成与 versions/ 目录名一致。启动器靠这个字段判断该运行哪个版本，不一致会以为需要更新，第一次启动就卡在下载上。
  2. 隔离数据目录。启动参数带 --user-data-dir，把 Electron 的 Cache、Cookies、Local Storage 指到该实例自己的目录；注入的 DLL 再把 Documents 一类 shell 文件夹 API 重定向到实例的 owndata。不隔离的话多个实例会共用 %APPDATA%\Tencent\QQ 与同一份原生数据，后启动的要么抢到前一个的登录态，要么直接抱怨"已在运行"。
  3. 给一个启动入口。生成 launch.bat，双击即可启动该实例的 QQ；正常流程是从 WebUI 点「启动」，由 start() 拉起同样的命令。

模板从一份完整官方客户端生成，按顺序查找：%QSICK_QQ_SOURCE%、{项目根}\QQNT-<版本>、%ProgramFiles%\Tencent\QQNT、%ProgramFiles(x86)%\Tencent\QQNT。找不到就是明确报错，不会静默建出一个起不来的实例。模板本身不随仓库分发（1.1 GB），已在 .gitignore 里。

          └─ 20–40 ms 内 CreateRemoteThread(LoadLibraryW) 注入 qsick_pipe.dll
               ├─ 隐藏窗口（IAT hook + 扫窗线程）
               └─ 重定向数据目录（Documents → 实例 owndata）

start() 按实例类型分岔，这是唯一的分歧点。pipe 不改客户端任何文件：application.asar、wrapper.node、major.node、package.json 这四个受校验文件一字节不动，校验必定通过；注入完全在内存里进行。之所以不能照抄 NapCat 改写 main 的思路，是因为该版本客户端对 package.json 做的是内容哈希校验——实测连只改缩进都会报「文件已损坏」，没有"小心地改"的余地。

为什么不用 CREATE_SUSPENDED。要求原本是"先凝滞 → 注入 → 恢复"，实测走不通：普通启动可以存活，而 CREATE_SUSPENDED + ResumeThread 会在约 12 秒后以 0x80000003 退出；连一个 DllMain 只 return TRUE 的空白 DLL 也复现，说明是挂起本身破坏了客户端初始化。于是改成正常启动、立刻注入：注入在 20–40 ms 内完成，远早于 Electron 创建窗口（通常要 1 秒以上），接管时机同样够用。
--no-sandbox 是必需的。不加它，QQ 会在启动约 12 秒后以 0x80000003 退出——即使完全不注入也一样。逆向笔记把校验定位在启动/sandbox 检查（QQNT.dll+0x26B6E3A 附近的 int3，0x26B6DFD 处读取 --no-sandbox），所以 pipe 的启动参数里始终带着它。实现细节见仓库的 pipe-injection.md。

多实例隔离

资源隔离方式验证
Electron userData（Cache、Cookies、Local Storage）--user-data-dir 指到实例自己的 userdata两个实例各自生成 userdata
原生数据根（Documents\Tencent Files）DLL hook shell 文件夹 API → 实例 owndata两实例 datadir=1，owndata 各 40+ 文件
单实例锁上述两者都隔离后自然不冲突同时运行互不干扰

实测同时启动 C1 与 C2：两个实例都存活、各有 3 个子进程、注入握手值均为 0xC0DE0001，进程树没有交叉，owndata 各自独立。

生命周期

  • 启动。start() 按类型分岔；状态文件刻意共用同一套字段（pid / phase / qr / uin …），额外写一个 transport: "pipe" 供排查。这样账户表、自动重登与聊天页都不需要为 pipe 分支。
  • 停止。stop() 不需要分支：它按 status.json 里的 pid 清理整棵进程树。pipe 实例不是单进程——QQ.exe 会派生 gpu/utility/crashpad 子进程，只杀主 PID 会留下孤儿并保持登录态。
  • 存活。QQ.exe 是 QSICK 的子进程，父进程退出后实例也随之结束；headless 实例则随 host.js 结束而停止。

05插件 API

插件是 plugins/ 下的一个目录，含一份 basic.json 清单和一个 Python 入口文件。它在进程内运行，与内核共用同一个事件循环，因此可以影响内核行为——这正是为什么清单必须事先声明意图，并由宿主强制执行。当前 API 版本为 1。

清单 basic.json

json
{
  "id": "guard",
  "name": "消息白名单 / 黑名单",
  "version": "1.0.0",
  "api": 1,
  "entry": "plugin.py:GuardPlugin",
  "tier": "core",
  "permissions": [
    "events.read",
    "events.drop",
    "config.read",
    "config.write",
    "runtime.read"
  ],
  "hooks": ["on_message"],
  "log": {"register": true},
  "priority": 10,
  "enabled": true,
  "description": "白名单外或黑名单内的消息在进入事件管线前丢弃。"
}
字段必填含义
id✅^[a-z][a-z0-9_-]{1,31}$，全局唯一
name / version✅用于显示与审计
entry✅file.py:ClassName；该类以无参方式构造
tier—sandbox < standard < core（默认 standard）。plugins.max_tier 会拒绝要求更高层级的插件
permissions—下表权限的子集；出现其他值即加载错误
accounts—允许收发的 QQ 号数组、["ALL"] 或省略；省略 = 账号无关
log / priority / enabled—日志分类注册；数值越小越先运行（守卫用 10）；false 时跳过该插件

权限模型

权限授予的能力未声明时的表现
events.read收到 on_message / on_event 调用钩子不会被调用，加载时告警
events.dropctx.drop()抛 PermissionDenied
messages.sendctx.send_group_msg / ctx.send_private_msg抛 PermissionDenied
actions.invokectx.call() / ctx.invoke_for()抛 PermissionDenied
actions.register注册或替换动作抛 PermissionDenied
config.read / config.writectx.read_config() / ctx.write_config()抛 PermissionDenied
runtime.readctx.runtime_info() / ctx.accounts()抛 PermissionDenied
core.hooks当前不授予任何能力—

未声明权限就调用对应 API 会抛 PermissionDenied，宿主记录并隔离本次调用；ctx.drop() 是唯一会向外传播的例外——它是控制流信号，不是错误。events.read 是真的会拦：实现了 on_message 却没声明它的插件，加载时得到一条警告，然后确实收不到消息。

账号范围有三种状态，别混淆：省略或 [] 表示账号无关，on_message 照常收到所有账号的消息，但不能调账号类接口；写具体号码表示只看、也只发这些号；["ALL"] 明确表示全部账号。省略与"全部"不是一回事，"忘了写"不该和"故意要全部"长得一样。账号类接口只认已登录的账号；拒绝分 AccountScopeUndeclared / AccountOutOfScope / AccountNotOnline 三种，判断顺序是先范围、后在线。只有 tier: "core" 的插件能用 ctx.restrict_account(uin, direction) 做内核级限制（in / out / both），且只在内存里生效。

生命周期钩子

python
class MyPlugin:
    def on_load(self, ctx):
        ...                              # 可以 async

    def on_message(self, message, ctx):
        ...                              # 返回 False / ctx.drop() 丢弃
        # message.account 是这条消息属于哪个号

    def on_event(self, event, ctx):
        ...                              # 返回 dict 替换，ctx.drop() 消费

    def on_unload(self, ctx):
        ...
  • on_message 在 URL 解析与存储之前运行；on_event 在映射之后运行，每个 OneBot 事件执行一次。
  • 返回 False 等价于丢弃，但需要 events.drop 权限；没有该权限的 False 会被忽略并告警。
  • 任何异常都会被捕获并记录；该插件在本次事件中被跳过，其它插件照常。
  • 热重载会监视插件目录下所有 *.py 与 basic.json，文件一变就重载（≤ 2 s）。

配置界面

basic.json 同时决定插件如何被配置。默认模式由 QSICK 渲染表单：

json
{
  "config_ui": "default",
  "config_fields": [
    {"key": "mode", "label": "模式", "type": "str", "default": "blacklist"},
    {"key": "groups", "label": "群名单（JSON）", "type": "json", "default": {"whitelist": [], "blacklist": []}},
    {"key": "log_drops", "label": "记录日志", "type": "bool", "default": true}
  ]
}

config_fields 的 type 支持 str / int / float / bool / json；字段可用 configEnable 指定控件与可见性（ifShow，控件 text / switch / select）。默认页面在 /plugins/<id>/config，保存会写入 data/plugins/<id>/config.json 并切换启用状态。config_ui: "custom" 时插件自带 HTML 页面，以 iframe 形式在 /plugins/<id>/config/page 提供（已做路径穿越防护），通过 GET / POST /api/plugins/<id>/config 读写配置。

插件市场

/plugins/market 列出部署在 plugins.market_url（默认 https://sickcc.online/QSICK/plugins-market）的服务，支持搜索、排序、点赞与安装/更新。安装时会下载归档包、校验 basic.json、解压到插件目录并热加载；服务端源码位于仓库的 market/。

安装它，就是执行它。插件与内核同进程运行。由于安装会执行第三方代码，可设置 plugins.allow_remote_install=false 直接禁用远程安装；只安装你读过或信任的插件。

故障隔离

  • 导入或 on_load 失败 ⇒ 插件不被加载，记录错误。
  • 钩子抛出异常 ⇒ 该钩子在本次事件中被跳过。
  • 钩子内出现 PermissionDenied ⇒ 记录后事件继续。
  • 没有 events.read ⇒ 钩子不会被调用（加载时已告警）。
  • 阻塞事件循环的插件确实会让一切卡住——请写异步代码，或用 asyncio.to_thread 把阻塞工作卸载出去。

参考插件：guard

plugins/guard/ 是白/黑名单参考实现。策略放在 data/plugins/guard/config.json（首次运行时创建），字段包括 mode（blacklist / whitelist）、scope（group / private / both）、groups 与 users 的双向名单、always_allow_users（绕过两种模式的号主账号）与 log_drops。它用 DEBUG 而非 INFO 记录丢弃——一个活跃的群可能丢弃上千条消息，那不算事故；清单里声明了 "log": {"register": true}，所以日志页能单独筛出 Plugin.guard。它没有 accounts 字段：只是旁观消息做判断，属于账号无关。

06Payload ABI

Python core 与原生载荷是各自独立的构建产物，二者以这份 ABI v1 为共同约定。凡未在此写明的内容，都属于实现细节。

传输

项目值
控制管道\\.\pipe\qsick.<pid>.ctl（请求，client → payload）
响应管道\\.\pipe\qsick.<pid>.rsp（应答，payload → client）
事件管道\\.\pipe\qsick.<pid>.evt（事件，payload → core，单向）
前缀覆盖QSICK_PIPE_PREFIX（载荷）/ transport.pipe_prefix（core）
编码小端序，正文为 JSON
并发每条管道同时只有一个在途请求；request id 用于关联应答

帧

32 字节头部，随后是 cmd | msg | body 三段、连续存放。

c
struct qsick_frame {      // 32 B，小端序
  uint32_t magic;         // +0   0x314B5351（"QSK1"）
  uint8_t  version;       // +4   必须为 1；不匹配即硬错误
  uint8_t  op;            // +5   见下文
  uint16_t flags;         // +6   保留
  uint32_t request;       // +8   请求 / 应答关联
  int32_t  status;        // +12  0 = 正常；负值 = 传输/载荷错误
  uint64_t value;         // +16  uin、sequence 等标量
  uint16_t cmd_len;       // +24  utf-8 长度，≤ 4096
  uint16_t msg_len;       // +26  utf-8 长度，≤ 65535
  uint32_t body_len;      // +28  字节长度，≤ 16 MiB
};                        // 之后依次为 cmd | msg | body（JSON / UTF-8）

Ops：1 HELLO、2 SEND、3 ACK、4 REPLY、5 EVENT、6 LOGIN、7 ERROR、8 PING、9 PONG、10 SHUTDOWN。

  1. core 连接控制、响应、事件三条管道；
  2. core 发送 HELLO（请求 id 为 1）；
  3. 载荷以状态 0 回复 HELLO；
  4. 载荷至少推送一次 LOGIN（{"logged_in":bool,"uin":"...","nickname":"..."}）；
  5. 只有在真实的 uin 到达之后，core 才把账号标记为就绪。

操作（SEND + cmd）

params 是一个 JSON 对象，应答 body 同样是 JSON 对象。成功时 status 为 0，否则 core 会上报 retcode = 1502。适配器动作以动作名作为 op 名，并将校验后的参数对象原样转发。

opparams结果
login.info—{uin, nickname}
status—{online, good, uin}
message.send{chat:{type,id}, elements:[...]}{message_id, seq, time}
group.members{group_id}[{uin, nickname, card, role}]
raw.call{cmd, body_hex}{status, body_hex}
oidb.call{command, sub_command, body_hex}{status, body_hex}

未知的 op 必须回复 status != 0 并附带一条可读消息，core 会把它映射为 retcode 1502 并继续运行。242 个动作里，74 个由内核直接支撑、永远不会到达载荷；其余 168 个是已注册但仍在等 QQ 侧线路实现的 payload op，完整清单见 docs/payload-ops.md。

事件（EVENT + cmd）

cmdbody
message.group / message.private消息信封（message_id、seq、time、chat、sender、elements）
message.sent账号自身发出的消息所对应的信封
notice.group_recall / notice.friend_recall{message_id, chat}
notice.group_increase / notice.group_decrease{group_id, user_id, operator_id}
notice.group_admin / notice.group_ban{group_id, user_id, ...}
request.friend / request.group{flag, user_id/group_id, comment}
noise.typing / heartbeat{chat, user_id}（core 只记 TRACE，从不转发）/ {}

core 能理解的元素类型包括 text, at, face, reply, image, record, video, file, json, xml, forward, mface, poke, markdown, flash_file, onlinefile, inline_keyboard；其他任何类型都按 unknown 保留——载荷随时可能发送新的类型。

钩子点、偏移表与蹦床

载荷必须暴露两个内部回调，并把它们桥接到事件：

  • send：在 QQ 发送 SSO 包之前以 (cmd, body) 调用；仅当有订阅方关心时才作为 EVENT 发布（core 目前并不订阅原始发送）。
  • recv：以 (cmd, body, uin, seq) 调用；解码为事件并发布。

偏移属于配置，而不是代码。环境变量 QSICK_HOOK_MODULE、QSICK_SEND_RVA、QSICK_RECV_RVA 可以针对单个构建覆盖偏移表：

json
{
  "entries": [
    {
      "version": "9.9.33-52230",
      "arch": "x64",
      "send": "367FE18",
      "recv": "36835CC",
      "verified": false,
      "note": "Cross-reference: NapCat packet.json；尚未在真实客户端验证"
    }
  ]
}
  • version 必须与客户端构建匹配（versions/<ver>/config.json 中的 curVersion）；send / recv 是相对 QSICK_HOOK_MODULE 的 RVA。
  • 只有 verified: true 的条目才会被使用；未验证条目会被拒绝，除非设置 QSICK_ALLOW_UNVERIFIED=1——错误的 RVA 会破坏客户端，而不是让操作失败。
  • 当偏移已设置但蹦床缺失时，脚手架会拒绝打补丁。这是有意为之：未挂钩的跳转会在无声无息中破坏客户端，而拒绝只是一行日志。

蹦床（trampoline.cpp）会整条复制指令，直到腾出足以容纳 12 字节绝对跳转（mov rax, imm64; jmp rax）的空间，然后修正 RIP 相对的 disp32 操作数并跳回 target + copied_len；它拒绝相对的 jmp / call / 短分支以及未知操作码。thunk 以同样的四个寄存器参数（Win64 整数 ABI）调用蹦床并返回 rax，从而保留原始调用；第四个之后的参数位于栈上，不会被转发——对 QSICK 针对的包入口点这不是问题，在别处则作为已知限制记录在案。调试时可用 QSICK_CAPTURE_ARG / QSICK_CAPTURE_LEN_ARG（0–3）指定持有 (pointer, length) 的寄存器参数，正文截断到 4096 字节并作为 trace.call 事件上报，core 仅以 TRACE 级别记录。

注入与管道认证

  1. find_qq_pids()（Toolhelp32）枚举 QQ.exe，最新的进程胜出。
  2. 如果 \\.\pipe\qsick.<pid>.ctl 已存在：直接附着。
  3. 否则 inject_dll(pid, payload)：OpenProcess → VirtualAllocEx → WriteProcessMemory → CreateRemoteThread(LoadLibraryW) → 等待。
  4. 轮询控制管道（8 秒），然后执行 HELLO 握手。

约束：64 位 Python、位数与 QQ 一致，以及当 QQ 以提权方式运行时需要提权。手动映射（manual mapping）有意未实现。

模式行为
random（默认）注入器为每个会话生成一个 128 位令牌，写入 <session_dir>/<pid>.token，载荷在引导阶段读取它。管道名变为 qsick.<pid>.<token>.ctl / .evt，HELLO.msg 必须等于该令牌。
fixed文件与管道名机制相同，但令牌来自 transport.pipe_token 或 QSICK_PIPE_TOKEN。
none使用普通管道名，没有令牌，也没有校验——仅用于本机单用户调试；core 会记录一条警告。

session_dir 默认为 %TEMP%\qsick\sessions，必须对 QSICK 与 QQ 进程都可写。令牌不匹配时表现为 status = -2、msg = "nonce mismatch"；core 会把它作为传输错误上报，而不是无限重试。管道按 PID 划分且仅限本地，它们保护的是机器，而不是管道本身。

锁定的 QQNT 版本

QSICK 瞄准一个官方 QQNT 版本：9.9.33-52230（x64）。它不修改、也不重新分发 QQ；启动器会检查已安装的客户端，必要时下载那个官方安装包（URL + SHA-256）。

bash
uv run qsick-launcher --check      # ready / version_mismatch / not_installed
uv run qsick-launcher --download <下载目录>

偏移来自该版本，并在 offsets.json 中标记为 unverified——它是对照 NapCat 的表交叉取得的，还没在真实客户端上验证。只在一次性账号上设置 QSICK_ALLOW_UNVERIFIED=1 抓包测试，成功后再把 verified 翻成真。分发的 DLL 是静态链接（/MT）：只导入 KERNEL32.dll 与 ADVAPI32.dll，因此不需要安装 VC++ 运行库；本次构建的版本与 SHA-256 记录在 BUILD.txt，可用 Get-FileHash 校验。

  • CPU 是整机占用，不是 QSICK 自己的。QSICK 的份额小到画不出形状。关闭的端点不显示——这一栏回答的是"应该监听的东西现在监听了吗"。
  • HTTP 没有连接数可数。它无状态，所以显示累计请求数，标签也照实写"次请求"；每块面板超过三行就滚动。

图表全部是手写 SVG（app.js 的 drawCpu / drawMemory / drawMessages），没有图表库：需要的东西只有折线、堆叠柱和环形图，而坐标系按实际像素设定，文字不会被拉伸。/static/app.js 与 app.css 的 URL 带 ?v=，值由文件 mtime 与大小算出，避免前端改动被缓存挡住。

实时日志与动作测试器

日志页走 SSE 实时流，可按级别、4 个分类组与关键词过滤，支持暂停、自动滚动、复制、下载与服务端清空。分类下拉框按已声明的分类填充，而不是按"已经出现过的记录"：核心分类随构建注册，插件分类必须在清单里写 "log": {"register": true}，否则一个从不写日志的插件不会出现在筛选里。

动作页列出全部 242 个动作，可按内核实现 / 适配器 / 类别过滤，并带一个 JSON 测试器——填参数、执行、结果可复制，用于在不写客户端代码的情况下验证某条链路。

登录密码与 access_token

webui.access_token 是给脚本用的共享密钥，密码是给浏览器里的人用的。两条并存，任一通过即可访问。

  • 密码只存 scrypt 摘要（含参数），位于 data/webui/auth.json，明文不落盘。
  • 会话 30 分钟，有操作即续期；改密码会让全部会话立即失效。
  • 登录记录（时间 + IP + 成功/失败）保留最近 100 条。
  • 首次访问且未设密码时，底部出现一条引导横幅，可关掉、7 天内不再问。它不挡界面——拒绝渲染直到设密码，会把刚装好软件的人锁在外面。
  • 除登录页外，所有页面与接口都要求令牌，/metrics 也在令牌之后；令牌用 secrets.compare_digest 比对，不做前缀匹配。

缓存清理

设置 → 缓存清理：左边一块环形图说明"谁占地方"，右边一张表说明"每项多大、怎么清"，外加一个一键清理。

缓存项位置清理动作
各账号原始消息库磁盘逐库清空并 VACUUM
消息缓存库磁盘清空 + VACUUM
日志缓冲区内存丢弃保留的日志行（不动日志文件）
WebUI 登录记录磁盘清历史，不动密码
媒体文件缓存磁盘删除目录下全部文件

配置、插件、登录密码不列为缓存——一个能删掉密码的「一键清理」是个陷阱。尺寸按文件系统量而不是按行数估：SQLite 的 -wal 常常比库本身还大，只报 .db 会把缓存量说小一大截。释放量是"清理前减清理后"的实测差值，不是清理代码的承诺；单项失败不打断「一键清理」，一项清不掉，其余的照清。

聊天栏已移除

WebUI 不再提供聊天界面。保留的是三个 group-only 老端点，给外部脚本用、不服务任何页面：GET /api/chat/groups、GET /api/chat/messages、POST /api/chat/send（受 webui.chat_enabled 控制，默认关）。消息内容的查看仍在消息页。
